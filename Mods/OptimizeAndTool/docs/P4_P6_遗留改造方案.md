## 1. P4 后台线程规范

### 1.1 现状与风险

`StructureMarker.cs` 中 `TriggerRescan()` 通过 `Task.Run` 执行 `ScanWorldStructures()`，存在三个问题：

| 风险点 | 现状 | 后果 |
|---|---|---|
| 共享状态读取 | 后台线程直接读 `Main.tile[x,y]`、`Main.chest`、`Main.dungeonX/Y`、`Main.maxTilesX/Y`、`Main.worldSurface` 等 | 玩家拆/放宝箱、挖掘、世界生成等主线程写操作与后台读并发；位块 `Tile` 对象可能被主线程替换导致读到撕裂数据（低概率但存在） |
| 线程外 UI 调用 | 扫描完成/失败后直接 `Main.NewText(...)` | `Main.NewText` 操作主线程 UI 集合（`Main.chatLine` 等），非线程安全；高负载下偶发异常或假死 |
| 竞态去抖 | `_isScanning` 是 `volatile bool`，扫描完成置回 | 逻辑本身正确；但扫描期间重复点击"重新扫描"静默失败，无用户反馈 |

### 1.2 目标

- 扫描主体保持在后台线程（方案架构约定，避免阻塞主线程）；
- 所有**游戏状态读取**在主线程内完成快照后再交给后台线程使用；
- 所有 **UI / 日志输出**经主线程队列调度；
- 扫描耗时用 `ScopedTimer` 实测并记录（验证方案"< 50ms"或修正预期）。

### 1.3 主线程队列设施（TPML 生态无 `MainThreadQueue`）

`OptimizeAndTool.csproj` 依赖 `TPML.Core` / `tContentPatch` / `CommandHelp` / `TPML.Content`，**不依赖** `TPMLBridge`，因此不能直接使用 `TPMLBridge.GABP.MainThreadQueue`。可行的主线程调度载体是 `tContentPatch.PatchMain` 提供的逐帧主线程钩子：

```csharp
// tContentPatch/ModPatch/Inheritance/PatchMain.cs
public virtual void UpdatePostfix(GameTime gameTime) { }   // Main.Update 后主线程调用
```

建议在 `StructureMarker`（已继承 `PatchMain`）内实现轻量队列：

```csharp
private static readonly System.Collections.Concurrent.ConcurrentQueue<Action> _mainThreadActions =
    new System.Collections.Concurrent.ConcurrentQueue<Action>();

/// <summary>把动作调度到主线程下一帧执行（UpdatePostfix 消费）</summary>
private static void RunOnMainThread(Action action)
{
    if (action != null) _mainThreadActions.Enqueue(action);
}

public override void UpdatePostfix(GameTime gameTime)
{
    while (_mainThreadActions.TryDequeue(out Action action))
    {
        try { action(); }
        catch (Exception ex) { Console.WriteLine($"[结构标记] 主线程任务异常: {ex}"); }
    }
}
```

### 1.4 扫描流程改造建议

```csharp
public override void OnEnterWorld()
{
    TriggerRescan();
}

public static void TriggerRescan()
{
    if (_isScanning) return;          // 去抖
    _isScanning = true;

    // ---- 主线程内快照（读取游戏状态，避免后台线程并发读）----
    // 注: Tile 引用数组本身巨大，完整拷贝不现实；
    // 建议折中：仅快照标量状态（maxTilesX/Y、worldSurface、rockLayer、dungeonX/Y、
    // chest 数组的 Length 与"每元素是否复用"标记），块数据读取仍放后台但接受低概率撕裂，
    // 或改为"分批在 UpdatePostfix 主线程推进扫描"（见 1.5 备选）。
    // 以下示例为标量快照 + 完成消息走队列的最小改法：
    int maxX = Main.maxTilesX, maxY = Main.maxTilesY;
    float worldSurface = Main.worldSurface, rockLayer = Main.rockLayer;
    int dungeonX = Main.dungeonX, dungeonY = Main.dungeonY;
    Chest[] chestSnapshot = Main.chest;

    _ = Task.Run(() =>
    {
        try
        {
            using (var timer = new ScopedTimer("StructureMarker.ScanWorldStructures", LogManager.GetLogger("OptimizeAndTool"), LogLevel.Info))
            {
                ScanWorldStructures(maxX, maxY, worldSurface, rockLayer, dungeonX, dungeonY, chestSnapshot);
            }
        }
        catch (Exception ex)
        {
            RunOnMainThread(() => Main.NewText($"[结构标记] 扫描失败: {ex.Message}"));
        }
        finally
        {
            _isScanning = false;
        }
    });
}
```

关键点：
1. `ScanWorldStructures` 改为**参数传入快照值**（不再直接读 `Main.*` 全局）；
2. `Main.NewText` 统一包一层 `RunOnMainThread(...)`；
3. 扫描耗时用 `ScopedTimer`（`TPML.Core.Diagnostics`，IDisposable）自动记录，`LogManager.GetLogger("OptimizeAndTool")`（`TPML.Core.Logging`）。

### 1.5 备选（更强一致，代价略高）

把全图块扫描改造成**主线程分步推进**：`UpdatePostfix` 每帧处理一段行区间（如 200 行/帧），约 12~20 帧完成一次全图扫描。优点：彻底消除并发读 `Main.tile` 的风险，扫描进度可以画进度条，且同样不阻塞渲染帧；缺点：实现复杂度略升，且"扫描中图钉不完整"窗口从亚秒变成半秒级。若实机验证 P4 最小改法无撕裂问题，可维持最小改法。

### 1.6 验收

- 进图后扫描完成/失败消息正常弹出，无异常日志；
- `ScopedTimer` 输出实际扫描毫秒数，与方案"< 50ms"对照并记录到 `WALKTHROUGH.md`；
- 重复点击"重新扫描"行为符合预期（去抖生效）。

### 2.4 推荐实现方式（防漂移）

与其手写 52+38 个 case（本次就是人工枚举导致的漂移），推荐**运行时查原版 API + 静态名称字典**：

```csharp
// 图标 ItemID 直接取自原版（与掉落/小地图图标天然一致，未来版本跟随原版）
int iconItemId = ChestChestStyle is Containers2 ? WorldGen.GetItemDrop_Chests(style, secondType: true)
                                                 : WorldGen.GetItemDrop_Chests(style, secondType: false);

// 名称/分类用静态字典（仅当已知样式缺失时回退 "宝箱 (样式 N)")
static string GetChestDisplayName(ushort tileType, int style) { /* 查下方字典/或保持手工 switch */ }
```

保留 `IsTrapped` 判定为**独立规则**（不依赖样式名）：
- `TileID.FakeContainers` / `FakeContainers2` → 一律 ChestTrapped（伪装陷阱）；
- Containers2 style 4 → ChestTrapped（死人宝箱）；
- （可选）Containers2 style 12/13 沙漠锁箱按实机确认是否带陷阱，保守归 ChestShadowBiome。

> 注：`WorldGen.GetItemDrop_Chests` 为原版公开方法（Publicizer 直连），`StyleId` 参与运算前需 `tile.frameX / 36`（与原版 `WorldGen.GetItemDrop_Chests(x, y, type)` 的内部推导一致，见 `WorldGen.cs:58497`）。

### 2.5 FakeContainers 细化（可选增强，低优先级）

`WorldGen.GetItemDrop_FakeChests`（`WorldGen.cs:42242`）给出伪装箱对应真实样式：Containers2 伪装箱 0=Crystal / 1=Golden / 2=Spider / 3=Lesion / 5=Solar 等。若希望浮窗显示"伪装成 XX 箱的陷阱"，可按该表细分；当前统一"伪装陷阱: 陷阱宝箱！"的提示已满足警示用途，可不做。

### 2.6 验收

- 实机在世界中放置/扫描各类箱子，核对图钉名称与图标与箱体一致（重点验证：蘑菇/花岗岩/大理石/黑曜石/地牢环境箱/沙漠锁箱/4 柱宝箱）；
- 陷阱判定：死人宝箱与伪装箱标红，普通箱不误标；
- `dotnet build` 0 警告 0 错误。
